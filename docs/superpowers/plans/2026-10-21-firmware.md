# Soccer Desk Display: Firmware Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Run the finished UI on the real Waveshare ESP32-S3-Touch-LCD-2.8 board: display, touch, Wi-Fi setup on the device, live data over HTTPS, pictures, battery and power button, updates over Wi-Fi, and the long-run reliability the gift needs.

**Architecture:** One PlatformIO project (`firmware/app/`) compiles the shared `ui/` library (LVGL 9.2 screens, store, poller, parsers) together with a thin board layer that implements the interfaces the UI already defines: `Backlight`, `Prefs`, `WifiService`, `HttpTransport`, `PowerService`, `ImageDecoder`. LVGL and all `ui/` calls run in ONE task; network work runs in worker tasks and hands results to the LVGL task through queues. Hardware facts come from the bring-up tests already run on the real board.

**Tech Stack:** C++17, PlatformIO platform `espressif32@8.0.0` (Arduino-ESP32 3.3.12, compiler xtensa-esp-elf 14.2), LVGL 9.2.2, ArduinoJson 7.4.2, ESP-IDF components reachable from Arduino (NVS, esp_http_client or NetworkClientSecure, SNTP, OTA, ADC).

**Specs:** `docs/superpowers/specs/2026-10-19-soccer-desk-display-design.md`, `docs/superpowers/specs/hardware-waveshare-esp32-s3-touch-lcd-2.8.md`, bring-up results in `firmware/bringup/` (branch `feat/firmware-bringup`, worktree `../socer-display-bringup`) and the earlier plan `docs/superpowers/plans/2026-10-19-soccer-display-sim-and-helper.md` (simulator and helper, done).

## Facts already verified on the real board (do not re-derive)

- Board is the V2 revision: touch chip CST3530 at I2C 0x58 on `Wire1` (SDA 1, SCL 3, INT 4, RST 2, reset: RST low 100 ms then high and wait 500 ms); the CST328 at 0x1A is absent. IMU 0x6B and RTC 0x51 on `Wire` (SDA 11, SCL 10). Touch coordinates are already screen coordinates: x 0..239, y 0..319, no transform.
- ESP32-S3 rev 2, 16 MB flash, 8 MB octal PSRAM (`qio_opi`), native USB serial on `/dev/ttyACM0` with `-DARDUINO_USB_CDC_ON_BOOT=1`.
- Display: ST7789 over SPI, MOSI 45, SCLK 40, CS 42, DC 41, RST 39, backlight GPIO5 (LEDC 20 kHz 10 bit); the vendor init sequence with INVON and little-endian pixel order is correct as in `firmware/bringup/src/display_st7789.cpp`; 40 MHz SPI works, 80 MHz is untested. The `bringup` environment (no swap, with inversion) shows correct colours, portrait with USB-C at the bottom, no mirroring.
- Power: GPIO7 must be driven HIGH early (power hold, needed on battery); GPIO6 is the power key (active low); battery voltage on ADC GPIO8 (`analogReadMilliVolts(8) * 3.0 * (1/0.990476)`, vendor values). With NO battery attached the ADC reads about 4.18 V (charger float), so a full pack on USB looks identical: battery presence cannot be detected by voltage.
- Battery: JLJLUP LP103665 3.7 V 3000 mAh with protection circuit, JST 1.25 mm 2-pin. Connector polarity is NOT yet verified against the board (multimeter procedure in `firmware/bringup/README.md`): nobody plugs it in before that check.
- Wi-Fi scan works (user's network seen at -79 dBm at the desk).
- Audio: PCM5101A I2S DAC plus 2 W amplifier, speaker header, hardware volume knob; I2S BCLK GPIO48, LRC/WS GPIO38, DOUT GPIO47, no MCLK (vendor `Audio_PCM5101.h`). No buzzer. Not yet tested on the real board. The user has two small speakers; whether the header is mono or stereo is unknown (Task 7a settles it).

## Global Constraints

- Flash 16 MB; PSRAM 8 MB octal; internal RAM is scarce (WiFi/LwIP, DMA buffers): large buffers (decoded images, LVGL heap, JSON documents) go to PSRAM.
- `ui/` stays pure and firmware-portable (no stdio, SDL, threads, libcurl, clock reads); everything the firmware adds lives under `firmware/app/` or in new pure files under `ui/src/` with sim tests. The simulator build (`sim/`) and its 551 tests must stay green after every task.
- Only the LVGL task touches LVGL objects and calls `ui/` functions. Worker tasks never do.
- Monotonic time is 64-bit and never wraps (`esp_timer_get_time()/1000`); the epoch clock is valid only after SNTP sync (year >= 2024): no TLS and no `app_refresh` epoch before that.
- Secrets (Wi-Fi passwords, helper token) are never logged, never printed on the serial console, never sent anywhere except the helper (token) or the router (password); the token and URL must not contain control characters (reject at load); HTTPS only on the device (no plain http).
- Wi-Fi: WPA2-Personal and open networks only; at least 8 (`kMinSavedNetworks`) saved networks, MRU order, auto-join the strongest saved network at boot and after a drop.
- Free tiers only; no extra paid services.
- Plain-English UI text; the user's priority is quality over speed (no deadline).
- Every task that touches the board ends with a **Board check**: exact commands, the serial lines to expect, and what the user should see. The board is attached to this machine at `/dev/ttyACM0` during development: the implementer may flash and read serial itself (never leave a stuck monitor process open, and never drive power-off tests without the controller's go-ahead); anything visible on the screen is checked by the user and reported (photo).

## Review Focus

1. **Boot without network or time:** no Wi-Fi, no SNTP, helper down: the UI still boots, shows "Connecting...", never loops on TLS errors with a wrong clock, never blocks the LVGL task.
2. **Power loss at the worst moment** (during an NVS write, during an OTA download, brown-out on battery): the device must come back with its saved settings or defaults and a working image (OTA rollback), never a boot loop. Tests: pure logic of the update decision with simulated failures, plus the documented board check.
3. **Days of uptime:** Wi-Fi drops and returns, helper 5xx, slow responses: stale marker, back-off, no heap or PSRAM leak, no task starvation (watchdog stays fed). Soak test in Task 12.
4. **Memory pressure:** allocation failure in a decoder, cache, JSON or LVGL must degrade (missing picture, skipped frame), never dereference null or reboot.
5. **Secrets handling and bad input:** control characters in token/URL/SSID/password, 32-character SSIDs, UTF-8 names, NVS keys longer than 15 characters (NVS limit), empty and corrupted NVS values.

### Task 4a: Sound in the UI library and the simulator (added 2026-10-21: the speakers that came with the board)

The board has a PCM5101A I2S DAC with a 2 W amplifier and a speaker header (pins in Facts below). This task builds everything that does not need the board: what sounds exist, when they play, how they are made, and how the user hears them on the PC. All pure, tested in the sim.

**Sounds (all synthesized in code, no audio files, mono 16-bit 16 kHz PCM):**

| Event | When | Sound |
|---|---|---|
| `Goal` | favourite team scores (same trigger as the goal screen) | air-horn style two-tone blast plus a rising crowd-noise swell, about 2.5 s |
| `WinFanfare` | favourite team wins at full time (after the whistles) | short major-key fanfare, about 2 s |
| `KickOff` | favourite team's match goes live | one referee whistle, about 0.6 s |
| `FullTime` | favourite team's match ends | three whistles (short, short, long), about 1.5 s |
| `BatteryLow` | battery banner appears at 15 percent (once per banner) | two soft beeps |
| `BatteryCritical` | 5 percent banner | three beeps |
| `WifiOk` | a join succeeds in Wi-Fi setup | one short rising chime |
| `Preview` | tapping `Test sound` in Settings | the `Goal` sound at the chosen volume |

Opponent goals and other teams' matches never make a sound.

**Settings (new, persisted):** `Sound`: `Off`, `Goals only` (Goal, WinFanfare), `Goals and match alerts` (adds KickOff and FullTime); battery beeps and WifiOk play whenever sound is not `Off`. Default `Goals only`. `Volume`: 20, 40, 60, 80, 100 percent, default 40. `Quiet hours`: on by default, sound is muted whenever night dimming is active (reuse `dim_schedule`), switch in Settings (`Mute at night`). Plain-English helper line under Sound: `The speaker only plays for your team.` A physical volume knob on the board scales the amplifier in addition to the software volume; mention it in the setup card, not in the UI.

**Files:** Create `ui/src/sound_event.h`, `sound_synth.{h,cpp}`, `sound_policy.{h,cpp}`, `sound_out.h`; modify `ui/src/settings.{h,cpp}`, `ui/src/app.{h,cpp}` (AppDeps field `sound`, nullable), `ui/src/screens/settings.cpp`, `ui/src/screens/goal.cpp` (emit `Goal`/`WinFanfare`), `ui/src/screens/battery_banner.cpp`, `ui/src/screens/wifi.cpp`, `sim/main.cpp`, `sim/CMakeLists.txt`; create `sim/sdl_sound.{h,cpp}`, `sim/tests/sound_*_test.cpp`.

**Interfaces:**
- `enum class SoundEvent { Goal, WinFanfare, KickOff, FullTime, BatteryLow, BatteryCritical, WifiOk, Preview };`
- `struct PcmClip { std::vector<int16_t> samples; static constexpr int kRate = 16000; };` and `const PcmClip& sound_clip(SoundEvent)`: generated once, deterministic (the crowd noise uses a fixed-seed integer PRNG, never `rand()`), peak at most 90 percent of full scale, 10 ms fade in and 30 ms fade out so there are no clicks, total of all clips at most 200 KB.
- `class SoundOut { virtual ~SoundOut(); virtual void play(const PcmClip& clip, uint8_t volumePercent) = 0; virtual void stop() = 0; virtual bool busy() const = 0; };` (the UI never calls it from a thread other than the LVGL one; firmware implementations queue internally).

- The UI calls `AppDeps::sound->play(...)` only through one helper `app_sound(Event)` in `ui/src/app.cpp` that applies `sound_should_play`, `SoundGate` and the volume, and does nothing when `sound` is null.
